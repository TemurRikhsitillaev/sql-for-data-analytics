# Ключи и JOIN

## Ключи

**PRIMARY KEY** — колонка (или набор колонок), однозначно определяющая строку. Уникален, не может быть `NULL`, в таблице ровно один. `products.product_id`, `orders.order_id`.

**FOREIGN KEY** — колонка, ссылающаяся на первичный ключ другой таблицы. `orders.customer_id` → `customers.customer_id`. СУБД следит за ссылочной целостностью: нельзя вставить заказ с несуществующим клиентом и нельзя удалить клиента, у которого есть заказы (без `ON DELETE`).

**Составной ключ** — ключ из нескольких колонок. `order_details` имеет `PRIMARY KEY (order_id, product_id)`: один товар встречается в заказе один раз, но и заказ, и товар по отдельности повторяются.

### Связи

| Тип | Как выглядит | Пример |
|---|---|---|
| один-к-одному | FK с уникальным ограничением | редко |
| один-ко-многим | FK на стороне «многих» | категория → товары |
| многие-ко-многим | таблица-связка с составным ключом | заказы ↔ товары через `order_details` |

Связка всегда разворачивается в два отношения «один-ко-многим»: заказ → позиции → товар.

## Синтаксис

```
FROM таблица_A
    [INNER | LEFT | RIGHT | FULL] JOIN таблица_B ON условие
```

```sql
SELECT p.product_name, c.category_name, p.unit_price
FROM products AS p
    JOIN categories AS c ON p.category_id = c.category_id
WHERE p.discontinued = 0
ORDER BY p.product_name;
```

`INNER` можно не писать — это значение по умолчанию. Алиасы таблиц почти обязательны: без них в запросе из трёх таблиц не разобраться, какой `category_id` чей.

## Виды JOIN

| Вид | Что оставляет |
|---|---|
| `INNER JOIN` | только строки, у которых есть пара в обеих таблицах |
| `LEFT JOIN` | все строки левой таблицы; где пары нет — `NULL` в колонках правой |
| `RIGHT JOIN` | зеркально; на практике почти не используется — проще поменять таблицы местами |
| `FULL JOIN` | все строки обеих таблиц, `NULL` с той стороны, где пары нет |
| `CROSS JOIN` | все комбинации каждой строки с каждой, без условия |

**Когда нужен `LEFT JOIN`.** Если в ответе должны быть нули — «все категории, включая те, где ничего не продали», «все клиенты, в том числе без заказов» — обычный `JOIN` такие строки выбросит, и в отчёте их просто не будет. Отсутствие строки заметить гораздо труднее, чем ноль.

```sql
SELECT c.company_name, COUNT(o.order_id) AS orders_count
FROM customers AS c
    LEFT JOIN orders AS o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.company_name;
```

Здесь важно `COUNT(o.order_id)`, а не `COUNT(*)`: у клиента без заказов `LEFT JOIN` даёт одну строку с `NULL`, и `COUNT(*)` насчитает единицу вместо нуля.

## ON против WHERE в LEFT JOIN

```sql
-- условие в ON: фильтрует правую таблицу ДО соединения
LEFT JOIN orders AS o
       ON o.customer_id = c.customer_id AND o.order_date >= '1997-01-01'

-- условие в WHERE: фильтрует результат ПОСЛЕ соединения
LEFT JOIN orders AS o ON o.customer_id = c.customer_id
WHERE o.order_date >= '1997-01-01'
```

Первый вариант оставит всех клиентов, в том числе без заказов 1997 года — у них будут `NULL`.

Второй **превращает `LEFT JOIN` во внутренний**: у клиента без пары `o.order_date` равно `NULL`, сравнение даёт `NULL`, и строка отсеивается. Классическая тихая ошибка.

Для `INNER JOIN` разницы нет — там условие можно писать где угодно.

## Размножение строк

Если одной строке левой таблицы соответствует несколько строк правой, **левая строка повторится столько раз, сколько нашлось пар**. Это не ошибка `JOIN`, а его определение: соединение возвращает все подходящие комбинации.

Заказ из 5 позиций после `JOIN order_details` даст 5 строк. Отсюда:

```sql
COUNT(*)                   -- посчитает позиции, а не заказы
COUNT(DISTINCT o.order_id) -- посчитает заказы
```

Второе правило: **после джойна «один-ко-многим» любой `COUNT` и `SUM` по левой таблице завышен.** Если в заказе 5 позиций, `SUM(o.freight)` просуммирует доставку пять раз.

Лечение — двухуровневая агрегация: сначала свернуть позиции до заказов в CTE, потом джойнить.

## Опечатка, превращающая JOIN в CROSS JOIN

```sql
JOIN orders AS o ON o.order_id = o.order_id
```

Обе стороны ссылаются на одну таблицу, условие всегда истинно, и получается декартово произведение. Запрос отработает, вернёт правдоподобные колонки и очень большие суммы.

Признак: выручка выросла в десятки раз, количество строк — кратно размеру второй таблицы. Проверка — `COUNT(*)` до и после джойна.

---

## USING и NATURAL JOIN

```sql
JOIN categories USING (category_id)
```

`USING` — сокращение для `ON a.category_id = b.category_id`, когда колонки называются одинаково. Дополнительно схлопывает их в одну колонку результата.

```sql
NATURAL JOIN categories   -- так лучше не писать
```

`NATURAL JOIN` сам соединяет по **всем** одноимённым колонкам. Если в обеих таблицах есть, скажем, `description` или `created_at`, они молча попадут в условие, и результат окажется неверным. Хуже того: добавление колонки в таблицу через полгода сломает давно работавший запрос. Явный `ON` — всегда.

## Несколько таблиц

```sql
SELECT o.order_id, c.company_name, p.product_name, od.quantity
FROM orders AS o
    JOIN customers     AS c  ON c.customer_id = o.customer_id
    JOIN order_details AS od ON od.order_id   = o.order_id
    JOIN products      AS p  ON p.product_id  = od.product_id
WHERE o.order_id = 10248;
```

Джойны применяются слева направо. Если хотя бы один из них `LEFT`, все последующие условия на эту ветку тоже должны учитывать возможные `NULL`.

## Чек-лист ошибок

| Симптом | Причина |
|---|---|
| Суммы выросли в разы | `JOIN` «один-ко-многим» без сворачивания или `ON` с одинаковыми алиасами |
| Количество заказов завышено | `COUNT(*)` вместо `COUNT(DISTINCT order_id)` |
| У клиента без заказов стоит 1 | `COUNT(*)` вместо `COUNT(o.order_id)` в `LEFT JOIN` |
| `LEFT JOIN` ведёт себя как `INNER` | Условие на правую таблицу стоит в `WHERE`, а не в `ON` |
| Нулевые строки пропали из отчёта | Нужен `LEFT JOIN`, а стоит обычный |
| Страна не та | `ship_country` (куда везут) вместо `customers.country` (где клиент) |
| Запрос сломался после изменения схемы | `NATURAL JOIN` |
